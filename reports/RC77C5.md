## Root Cause

### CI Failure: `pytest pruebas/` (exit code 5)

The CI pipeline `ci.yml` was executing `python -m pytest pruebas/` which collected **0 tests** because the `pruebas/` directory contains **no Python files** — only 68 PowerShell `.ps1` test files, 1 `.psm1` module, and 1 `.json` config. pytest exits with code 5 when no tests are collected, causing the CI to fail.

### Startup Command Inconsistency

The `deploy.yml` pipeline specified a startup command **without `--timeout 600`**, while `provision-appservice.yml` included it. The Azure App Service currently reflected the `deploy.yml` version (without timeout), creating a cold-start risk for long-running deployments.

### CI Gaps

1. No entrypoint validation (`Hermes.Web.backend.main:app`)
2. No Pester test execution (68 PowerShell tests never run in CI)
3. Build job used `shell: pwsh` on `ubuntu-latest` (fragile)

## Lessons Learned

1. Azure App Service Python must not depend on auto-detection of entrypoint. Always set an explicit startup command.
2. FastAPI requires an ASGI server correctly configured. Gunicorn must use UvicornWorker.
3. `sleep` is not a robust readiness strategy. Use HTTP polling with retries.
4. CI must not execute `pytest` against non-existent Python suites. Exit code 5 (no tests collected) must be handled explicitly.
5. PowerShell/Pester tests and Python tests are distinct. Each must be validated separately.
6. YAML must be validated before deployment. Unicode emoji characters can cause encoding issues on Windows.
7. An HTTP 200 does not prove the correct application is deployed. Semantic identity validation is required.
8. Startup command must be consistent across all workflow files. A mismatch between `deploy.yml` and `provision-appservice.yml` causes silent drift.
9. Application identity must be cross-validated (health + version + OpenAPI) to confirm Hermes Enterprise is serving requests.
10. Evidence artifacts should include semantic assertions, not just HTTP status codes.
11. Inline multi-line Python in GitHub Actions YAML `run: |` blocks causes IndentationError because YAML common-indent stripping leaves leading whitespace that Python rejects at module level. Use stdin piping (`echo "$VAR" | python3 -c "code"`) to avoid indentation issues.
12. Pre-existing Pester test failures (path assumptions, drive mappings) should not block CI. Syntax validation is the appropriate gate for PowerShell when tests are designed for local Windows environments.
