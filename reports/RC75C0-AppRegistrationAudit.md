## 6. Compatibility Analysis for Hermes

### Can it authenticate via OIDC?
✅ Yes — Azure AD App Registrations support federated credentials.

### Can it deploy a Web App?
✅ Yes — Contributor at subscription level is more than sufficient.

### Does it have EXCESSIVE permissions?
🔴 **YES. Severely excessive.** Hermes only needs:
- Contributor on `RG-Hermes-Proyectos` (not subscription)
- No Microsoft Graph API permissions needed for OIDC deploy

### What minimum permissions does Hermes actually need?
- **RBAC:** Contributor on `RG-Hermes-Proyectos` only (scoped to the RG, not subscription)
- **API permissions:** NONE — OIDC federated credential authentication does not require Microsoft Graph or any other API permissions
- **Federated credential:** One per project repository

## 7. Risk of Reusing UR - App - SII 2.0

### Risks
1. **Subscription-wide Contributor** — if GitHub Actions is compromised, attacker gains control of ALL Azure resources, not just Hermes projects
2. **Directory.ReadWrite.All** — can read/write all Entra ID directory objects
3. **Application.ReadWrite.All** — can modify/delete other App Registrations (including SII 2.0 itself)
4. **AppRoleAssignment.ReadWrite.All** — can self-elevate privileges
5. **13 client secrets** — each is a potential attack surface
6. **SII 2.0 dependency** — any change to the App Registration affects SII 2.0 operations
7. **Audit contamination** — GitHub Actions logs would mix SII 2.0 operations with Hermes operations

### Verdict

> ## 🔴 DO NOT REUSE
>
> "UR - App - SII 2.0" is an institutional application with effectively **full administrative access** to both Azure subscription and Entra ID. Reusing it for Hermes would:
> - Expose SII 2.0 operations to any compromise in the GitHub Actions pipeline
> - Grant GitHub more permissions than architecturally necessary
> - Violate the principle of least privilege
> - Create audit ambiguity between SII 2.0 and Hermes operations

## 8. Recommended Architecture

```
NEW App Registration: "Hermes-Enterprise-OIDC"
├── RBAC: Contributor on RG-Hermes-Proyectos ONLY
├── API Permissions: NONE (not needed for OIDC deploy)
├── Federated Credential 1:
│     ├── Subject: repo:FREDYASARMIENTOT/HERMES-ENTERPRISE:environment:production
│     ├── Issuer: https://token.actions.githubusercontent.com
│     └── Audience: api://AzureADTokenExchange
├── Federated Credential 2:
│     ├── Subject: repo:FREDYASARMIENTOT/<Proyecto>:environment:production
│     └── (one per project repository, not wildcard)
└── NO client secrets (zero trust, OIDC only)
```

### Why not wildcard `repo:FREDYASARMIENTOT/*`?
Per the instructions: wildcard subject claims should be avoided without explicit architectural justification. Each project repository should have its own federated credential (or use organization-level credentials with environment-based scoping if approved).
